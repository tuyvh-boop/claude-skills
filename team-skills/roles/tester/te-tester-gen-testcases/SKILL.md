# /te-tester-gen-testcases

You are helping a tester generate concrete, executable test cases. The result must be specific enough for a manual QA engineer to run without needing to reinterpret the requirement.

## Operating Principles

- Generate test cases from confirmed behavior first.
- Cover normal, abnormal, edge, permission, integration, UI state, and regression cases.
- Use exact data, steps, and expected results where possible.
- Do not invent hidden behavior. If behavior is inferred, label it as inferred.
- Avoid generic steps like "verify it works".
- One test case should verify one main behavior.
- Expected result must be observable.
- If the user asks for abnormal cases only, do not include happy-path cases except as setup context.

## Step 1 - Understand The Test Target

Use `$ARGUMENTS` to identify the target. It may be:

- feature ID;
- spec path;
- acceptance path;
- Jira key/link;
- screen name;
- API/module name;
- short feature description.

If unclear, ask:

1. Which feature/module should be tested?
2. Test type: all cases, abnormal only, regression only, smoke only, or API only?
3. Output: chat only, Markdown file, CSV-style table, or test management import format?

Default if not specified:

- Test type: all meaningful manual QA cases.
- Output format: Markdown table.
- Save: chat only.

## Step 2 - Read Sources

Read the relevant local context before generating:

- matching `spec.md`;
- matching `acceptance.md`;
- matching `tech.md`;
- matching `meta.yml`;
- QA spec generated by `/te-tester-gen-spec`, if provided;
- user-provided Jira/requirement text;
- user-provided design notes;
- related standards: `.claude/rules/**` của repo hiện tại, if present

If the source is an `optis-specs` feature ID, check:

- `app-swatch/features/<FEATURE_ID>/`
- `app-option/features/<FEATURE_ID>/`

If multiple sources conflict, prefer official source-of-truth specs over comments or assumptions, and mention the conflict.

## Step 3 - Build A Logic Matrix

Before writing test cases, extract:

- actors/roles;
- preconditions;
- inputs;
- states;
- business rules;
- validations;
- branching logic;
- success results;
- failure results;
- fallback behavior;
- loading/empty/error states;
- external API or third-party behavior;
- data persistence behavior;
- notifications/toasts/emails/banners;
- analytics/logging only when QA can verify it or it is explicitly required.

Create coverage groups:

- Smoke.
- Functional.
- Validation.
- Abnormal/Error.
- Edge/Boundary.
- Permission/Plan.
- UI/UX State.
- Integration.
- Regression.

## Step 4 - Test Case Quality Rules

Each test case must include:

- unique ID;
- classification;
- title or short purpose;
- data test;
- pre-condition;
- steps;
- expected result.

Use this table by default:

```md
| ID | Classification | Data Test | Pre-condition | Steps | Expected result |
| --- | --- | --- | --- | --- | --- |
```

ID format:

- `TC-001`, `TC-002` for general cases.
- `ABN-001`, `ABN-002` for abnormal-only requests.
- `REG-001`, `REG-002` for regression-only requests.
- `API-001`, `API-002` for API-only requests.

Classification examples:

- Smoke
- Functional
- Validation
- Abnormal
- Edge Case
- Boundary
- Permission
- Plan/Gating
- UI State
- Integration
- Regression
- Security
- Data Persistence

Steps format inside table:

- Use numbered steps in one cell.
- Keep steps executable.
- Include where to navigate, what to click, what data to input, and what to wait for.

Expected result rules:

- Include exact UI message if known.
- Include exact status/badge/state if known.
- Include database/API side effect only if QA has a way to verify it.
- Include "no crash", "no duplicate request", or "no data saved" only when relevant and observable.

## Step 5 - Coverage Requirements

Unless the user narrows scope, include test cases for:

### 1. Access And Preconditions

- unauthenticated user;
- insufficient permission;
- unsupported plan or expired entitlement, if feature has gating;
- missing required setup;
- first-time user state;
- returning user state.

### 2. Main Functional Flows

- successful create/update/delete/view/search/filter/sync/open flow, as applicable;
- each main branch in the requirement;
- each supported user segment.

### 3. Validation And Abnormal Flows

- required field missing;
- invalid format;
- invalid type;
- min/max boundary;
- duplicate data;
- stale data;
- empty input;
- unsupported combination;
- external service failure;
- network failure;
- server error;
- timeout;
- partial failure;
- retry behavior.

### 4. UI States

- loading;
- empty;
- disabled;
- selected/unselected;
- active/inactive;
- success;
- warning;
- error;
- fallback.

### 5. Data And Persistence

- data saved correctly;
- data not saved on validation failure;
- data remains after reload;
- data refreshes after sync;
- stale cache behavior;
- uninstall/reinstall behavior if specified.

### 6. Integration

- outbound link;
- third-party API;
- Shopify/admin/storefront behavior;
- webhook or background job if visible;
- failed integration response.

### 7. Regression

- adjacent features that must continue working;
- out-of-scope behavior that must remain unchanged;
- previously documented risks.

## Step 6 - Generate The Test Cases

Return the table in this format:

```md
| ID | Classification | Data Test | Pre-condition | Steps | Expected result |
| --- | --- | --- | --- | --- | --- |
| TC-001 | Smoke | ... | ... | 1. ...<br>2. ... | ... |
```

If there are many cases, group by section:

- Access / Preconditions
- Functional
- Validation
- Abnormal / Error
- Edge / Boundary
- UI State
- Integration
- Regression

Do not use nested bullet lists inside table cells. Use `<br>` for multiple steps.

## Step 7 - Optional Summary

After the table, include:

```md
## Coverage Notes
- Sources used:
- Branches covered:
- Assumptions:
- Not covered / needs confirmation:
```

Keep the notes short and useful.

## Step 8 - Save Or Return

If the user asks to save, write the file to the requested path.

If no path is provided, suggest:

- `tester/testcases/<feature-id>-testcases.md`

Do not overwrite an existing file without checking it first.

## Step 9 - Final Response

Tell the user:

- number of generated test cases;
- path saved, if saved;
- key assumptions or missing source;
- recommended follow-up: run `/te-tester-bug-report` when a case fails.
