# Plan Sources Core — Jira + Design + Code (dùng chung)

## ⚠️ Framework Reminder

Plan sources must be gathered systematically and verified across layers: [[framework_systematic_problem_solving]] —
- **Measure depth per purpose**: reviewing a plan requires different depth than creating one. Spot-check vs full audit depend on what decision the finding supports
- **Verify source conflicts early**: Jira says X, design shows Y, code does Z → stop and ask user to decide before proceeding. Don't inherit conflicting assumptions into plan
- **Trust verified sources, verify hypothesis**: CodeGraph results are trusted (full AST). Explore agent + grep results merit spot-check before influencing critical decisions (risk P0/P1, architecture)

## Nguyên tắc tiết kiệm token

- **Không dò lại thứ đã biết.** Project key Jira lấy thẳng từ bảng trong `shared/CLAUDE.md` (OPOS/OPOK/OPCS/OPSK) — không gọi `getVisibleJiraProjects`/`getAccessibleAtlassianResources`.
- **Đang ở giữa 1 chuỗi create-plan → review-plan → fix-plan trong CÙNG phiên?** Dữ liệu Jira/design/code đã fetch ở skill trước còn nguyên trong context → **tái dùng thẳng, đừng fetch lại**. Chỉ fetch lại khi: đổi mã Jira, dữ liệu đã cũ (khác phiên), hoặc cần verify 1 claim cụ thể chưa rõ.
- **Fetch song song những gì biết trước, không ép song song thứ chưa biết.** Jira và code-recon là 2 việc độc lập biết trước → gọi `Agent` cho cả 2 cùng lúc (1 message, nhiều tool call). Design thường **chưa biết có cần fetch hay không** cho tới khi đọc xong Jira — không cố ép fetch song song nếu chưa rõ có link; chấp nhận thêm 1 round-trip cho design sau khi Jira trả về.
- **Subagent trả về bản tóm tắt, không trả nguyên văn** — NHƯNG luôn dặn thêm: "nếu phát hiện gì quan trọng ngoài phạm vi câu hỏi (vd code đã có sẵn WIP/branch khác giả định, pattern trùng lặp, dependency chặn go-live), báo lại dù không được hỏi." Nhiều phát hiện quan trọng nhất nằm ngoài câu hỏi ban đầu.
- **Design là tuỳ chọn, nhưng phải tự tìm trước khi coi là "không có".** Ưu tiên link `figma.com` user đưa trực tiếp; nếu không có, sau khi Jira trả về, **tự kiểm tra description/comment của Jira có link `figma.com` không** (rất thường có, nằm trong mô tả ticket) rồi mới quyết định bỏ qua trục Design. Chỉ bỏ hẳn khi cả 2 nguồn đều không có link.
  - Node Figma là 1 board/overview lớn (không phải 1 frame cụ thể) → gọi `get_metadata` trước để tìm node con cần xem, đừng `get_screenshot` thẳng node gốc (ảnh sẽ không đọc được chữ). `get_metadata` của cả board cũng có thể vượt giới hạn output; nếu tool không có tham số giới hạn độ sâu (thực tế thường chỉ nhận `nodeId`) — dump kết quả ra file tạm rồi `grep` tên field/label cần tìm để định vị nodeId gần đúng (parse theo thụt lề), đừng gọi lại nhiều lần với hy vọng có tham số depth không tồn tại.
  - **Chọn đúng node trong board lớn cần phán đoán qua lại nhiều vòng** (metadata → dò ancestor chain → screenshot → tự sửa nếu chọn sai, tên frame dễ trùng lặp) — làm việc này ở **main loop**, gọi Figma MCP trực tiếp thay vì giao hẳn cho subagent (subagent không tự "nhìn" ảnh để tự sửa lỗi chọn sai node). Chỉ giao sang subagent phần tóm tắt nội dung SAU KHI đã chốt đúng node.
- **Code hiện tại: ưu tiên CodeGraph** (`codegraph_search`/`codegraph_context`/`codegraph_impact`) — nhưng xác nhận có **tool thật** dùng được (thử gọi hoặc `ToolSearch "codegraph"`), KHÔNG chỉ dựa vào việc thấy thư mục `.codegraph/` tồn tại (thư mục có thể rỗng/chưa index → false positive). Không có tool CodeGraph thật → `Agent(subagent_type: "Explore")` với phạm vi hẹp (chỉ module/file liên quan tới mã Jira/plan), kèm 1 lệnh `git status`/`git branch` để phát hiện WIP chưa commit trên branch hiện tại.
  - **Độ sâu verify phụ thuộc mục đích, không phải 1 con số cố định.** Mục đích là **chấm điểm** (review-plan) → Explore agent report đủ, chỉ spot-check trực tiếp 1-2 claim quan trọng nhất (xem bullet "Ranh giới tin tưởng" dưới). Mục đích là **thiết kế tiếp** (create-plan) hoặc **sửa theo finding cụ thể** (fix-plan, khi finding đó chạm code) → Explore agent chỉ định vị đúng file, main loop phải **tự đọc trực tiếp** các file trong vùng thay đổi chính (không dừng ở spot-check) vì cần thấy đủ chi tiết (field nào thiếu ở tầng nào, logic thật đang chạy ra sao) để viết plan đúng — Explore report tốt cỡ nào cũng dễ bỏ sót gap tinh vi (field thiếu ở DTO nhưng có ở schema, hay ngược lại).
- **Việc fetch → subagent (Haiku/Sonnet tuỳ độ phức tạp); việc phán đoán/thiết kế/so sánh → main loop (Sonnet/Opus).** Đừng để main loop tự đọc description Jira dài hay lướt cả file design — để agent tóm tắt trước.
- **Tách bạch 2 loại tài liệu, đừng để lẫn vào nhau.** `create-plan`/`fix-plan` tạo ra **bản PLAN** (`<mã Jira>-plan.md`) — tài liệu để dev đọc và code theo, viết bằng ngôn ngữ xây dựng ("làm X", "thêm Y ở Z"), tổ chức theo khu vực tính năng (Frontend/Backend/theo feature), KHÔNG bao giờ chứa ngôn ngữ audit/review ("đã verify", "vi phạm AC", "xác nhận qua đọc code", nhãn mức độ P0/P1/P2, checklist "finding đã xử lý"). `review-plan` tạo ra **bản REVIEW** (`<mã Jira>-plan-review.md`) — tài liệu chấm điểm, được phép và nên dùng đúng ngôn ngữ đó. `fix-plan` đọc cả 2 file này nhưng chỉ ghi lại/cập nhật file **plan**, giữ nó sạch — mọi vết tích "đã sửa gì theo finding nào" (nếu cần lưu vết) thuộc về file **review**, không trộn vào file plan. Sau vài vòng review→fix liên tiếp, nếu không cẩn thận file plan sẽ dần biến thành nhật ký audit — luôn tự hỏi trước khi ghi: "câu này có phải thứ dev cần đọc để BIẾT LÀM GÌ, hay chỉ là vết tích của việc mình vừa soát/sửa cái gì?" — chỉ giữ loại đầu trong file plan.
- **1 lượt review không đảm bảo exhaustive.** `review-plan` chấm càng sâu càng lộ thêm gap ở AC section nó chưa từng chạm tới — đừng coi report của 1 lần review là danh sách đầy đủ mọi vấn đề. `fix-plan` chỉ vá đúng những gì report liệt kê sẽ kế thừa luôn điểm mù đó — vì vậy trước khi coi 1 vòng `create-plan`/`fix-plan` là xong, nên có 1 bước tự quét completeness ở mức section-level (không cần đào sâu lại), và coi pipeline `create-plan → review-plan → fix-plan` là **hội tụ** khi 2 lần `review-plan` liên tiếp không tìm thêm gì mới (hoặc đạt verdict 🟢) — không phải cứ chạy đúng 1 vòng review→fix là mặc định xong.
- **Ranh giới tin tưởng kết quả subagent:** kết quả từ **CodeGraph** (full AST) tin thẳng, không cần verify lại. Kết quả từ **Explore agent** (dựa trên grep/Read, có thể bỏ sót hoặc suy diễn sai) — với claim nào sẽ quyết định 1 kết luận quan trọng (rủi ro P0/P1, hoặc 1 quyết định thiết kế không đảo ngược được), tự `grep`/`Read` spot-check lại 1-2 điểm quan trọng nhất trước khi dùng, đừng lan truyền lỗi của agent xuống kết luận cuối.

## Cách thu thập (2 đợt)

**Đợt 1 (song song, 1 message nhiều Agent tool call):**

- **Jira**: `Agent` fetch `getJiraIssue` (site `optis-app.atlassian.net`, cloudId `0324d786-4e6b-4cdf-bd05-8d876d21f3a7`, issueIdOrKey = mã) → yêu cầu trả về: title, mô tả ngắn, **toàn bộ acceptance criteria** (không tóm lược mục này), Change Size nếu có, và **mọi link `figma.com` xuất hiện trong description/comment**.
- **Code hiện tại**: `Agent` (CodeGraph nếu có tool thật, không thì Explore + `git status`) khảo sát vùng code liên quan — trả về: module/file liên quan đã tồn tại (kể cả WIP chưa commit), pattern/helper sẵn có nên tái dùng, ràng buộc kỹ thuật hiện tại (schema, API contract, dependency) có thể ảnh hưởng.

**Đợt 2 (chỉ khi cần):** có link Figma (từ user hoặc vừa lộ ra trong Jira ở Đợt 1) → `Agent` gọi Figma MCP (`get_metadata` để định vị frame cụ thể trước nếu node là board lớn, rồi `get_screenshot`/`get_design_context` cho đúng frame) → yêu cầu trả về: state/flow chính, field/component quan trọng, không paste raw node tree. Không có link ở cả 2 nguồn → bỏ hẳn trục Design.

Thiếu nguồn nào (không có Jira, không có design) → bỏ qua, không tạo giả định thay.
