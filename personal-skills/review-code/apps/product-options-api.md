# App Profile: product-options-api

> Repo: `sa-division/te-team/sa-swatch-app` nhánh Product Options — SAPO/api (`OPTIS Product Options` / BSS Product Options Builder).

## Kiến trúc & luồng chính
- Stack: NestJS 11 + Prisma 7 (MySQL/MariaDB qua `@prisma/adapter-mariadb`). Module theo chuẩn Nest (`src/modules/<feature>/`), repository pattern qua `src/database/repositories/<name>/` (interface + impl + index + spec).
- Đang chạy song song 2 runtime storefront: V1 (theme app extension `tae`, đọc metafield app-data) và V2 (`tae-v2`, đọc 4 loại Shopify metaobject app-owned `$app:bss_po_*`). Cột `shops.storefront_runtime_version` (`v1`/`v2`) là công tắc; cron 15 phút (`StorefrontV2DriftCronService`) phản chiếu cột này ra metafield `BSS_PO_RUNTIME` cho theme liquid đọc.
- Trigger đồng bộ dùng lại đúng 1 event có sẵn `SHOP_CONFIG_EVENTS.UPLOAD_REQUESTED` (`@nestjs/event-emitter`) — V1 và V2 listener độc lập hoàn toàn, cùng nghe 1 event, lỗi bên nào không được chặn bên kia.
- Metaobject Admin API: `MetaobjectService` (`src/modules/metaobject/`) là lớp dùng chung để gọi Shopify Admin GraphQL cho metaobject/definition. `ensureDefinition()` tự kiểm tra + tạo definition trước khi ghi lần đầu (không cần setup tay qua GraphiQL).

## Quy ước bắt buộc của app
- **Mọi thay đổi `prisma/schema.prisma`** (thêm/sửa bảng, cột, quan hệ, index) **bắt buộc** phải cập nhật cùng commit: `schema_annotations.yaml` (luôn) và `DATABASE.md` (khi đổi bảng/quan hệ/cascade/index — không chỉ đổi 1 cột đơn thuần). Đây là quy tắc ghi rõ trong `CLAUDE.md`, đã bị bỏ sót ít nhất 2 lần liên tiếp trong cùng 1 task (OPOS-136) — soi kỹ mỗi khi diff chạm `prisma/schema.prisma`. — `Áp dụng khi: db-schema`
- **Tái dùng helper V1 có sẵn** thay vì viết lại khi build tính năng song song (V2): ví dụ `sortOptionSetsByPriorityRule`, `mapOptionSetToStorefront`, `normalizeStorefrontPlanCode`, `withShopifyRetry`, `extractIdFromGid`. Đối chiếu diff mới có tự viết lại thứ đã tồn tại ở module `option-set`/`common/helpers` không. — `Áp dụng khi: logic, structure`
- **Mọi lệnh gọi Shopify Admin API ghi dữ liệu** (`upsert`, `createDefinition`, `ensureDefinition`) nên bọc `withShopifyRetry` nhất quán — không chỉ bọc lệnh `upsert()` chính mà bỏ sót bước chuẩn bị (vd `ensureDefinition()`), vì 1 lỗi transient (`THROTTLED`) ở bước chuẩn bị có thể chặn toàn bộ phần còn lại của 1 lượt sync. — `Áp dụng khi: external-call`

## Vùng nóng / dễ vỡ (hotspots)
- `src/modules/storefront-v2-sync/` — module dual-write mới, map dữ liệu Option/OptionSet cũ (schema Sequelize/Prisma denormalized) sang JSON contract V2. Đối chiếu kỹ với `metaobject-data-contract-v2.md`/OpenSpec `backend-metaobject-sync` khi review vùng này — nhiều mapping best-effort/suy diễn từ V1 code thật (ghi rõ trong comment), dễ lệch nếu spec đổi mà mapper không cập nhật theo. — `Áp dụng khi: logic`
- `src/modules/metaobject/metaobject.service.ts` — lớp dùng chung gọi Shopify Admin API cho MỌI module (V1 lẫn V2). Đã sửa (`createDefinition`/`upsert` giờ đọc `userErrors` trước khi throw, `getByHandles()` chia batch ≤250 handle) — nhưng vẫn là điểm MỌI Admin API call mới trong module này đi qua, nên mọi thêm-mới ở đây (query/mutation mới) phải soi lại đúng 2 tiêu chuẩn: đọc `userErrors`, và nếu trả về danh sách theo `handle:`/`query:` filter thì phải tự chia batch (Shopify không tự phân trang query kiểu này). — `Áp dụng khi: external-call`
- Cron `StorefrontV2DriftCronService` từng dùng `findMany({ take: 50 })` không `orderBy` xoay vòng — đã bỏ hẳn `take` (cột `storefrontRuntimeVersion` default `'v1'` nên `not: null` khớp MỌI shop, không phải nhóm nhỏ; quy mô hiện tại chấp nhận full-scan mỗi 15 phút). Soi mọi cron/batch job MỚI có pattern `take` cố định mà thiếu `orderBy`/cursor xoay vòng — lớp lỗi này đã xảy ra thật ở đây một lần. — `Áp dụng khi: async`

## Bẫy tái diễn (pattern-level)
- **Bỏ key khỏi payload `metaobjectUpsert` không xoá giá trị cũ** (suy từ docs Shopify — `fields` chỉ cập nhật key được gửi; chưa đo trên store thật): `MetaobjectService.upsert` gửi `metaobject: { fields }` chỉ gồm key có mặt. Mapper Store Config V2 (`store-config.mapper.ts`) có pattern "chỉ set cờ khi `true`, omit khi tắt" → cờ đã từng `true` có thể không bao giờ về `false`. Khi review mapper metaobject đổi một cờ/field từ "có" sang "không", đòi ghi tường minh (`false`/rỗng) thay vì omit. — `Áp dụng khi: logic, external-call`
- **Bảng plan/feature có nhiều bản sao** (cms `app/shared/constants/pricing.ts` là gốc; api có `storefront-v2-sync/entitlements/pricing-plans.constant.ts` và `sidekick/constants/pricing-plans.constant.ts`): đổi rule ở một bản mà không đổi các bản kia là lệch hành vi editor ↔ storefront. Soi cả ngữ nghĩa *khoá thật* trong editor cms (component nào khoá bằng feature nào), không chỉ tên key trong bảng — vd multi-select dropdown bị khoá bằng `LIMIT_SELECTOR` chứ không phải `MULTIPLE_SELECT`. — `Áp dụng khi: logic`
- **Task rebuild/song song 2 hệ thống (V1 song song V2) dễ quên tính idempotency đã ghi trong plan**: khi kế hoạch đã chốt cần bảng "sync state" (lastPushedVersion/syncedAt) để skip ghi trùng, nhưng lúc code thực tế bị thiếu — triệu chứng dễ nhận: có unit test đặt tên đúng mô tả hành vi sai (vd "vẫn upsert lại dù payload không đổi") nhưng test đó PASS vì assert đúng cái hành vi thiếu, không phải verify tính năng hoạt động. Khi review, đọc kỹ *tên* test lẫn *assertion* — tên mô tả hành vi tiêu cực + test pass = dấu hiệu tính năng plan yêu cầu chưa được implement, không phải bug test. — `Áp dụng khi: logic, test`
- **DB schema thêm bảng/cột mà quên cập nhật tài liệu bắt buộc** (`DATABASE.md`/`schema_annotations.yaml`) — đã xảy ra lặp lại trong cùng 1 task, ở các mức độ khác nhau (thiếu 1 cột → sau đó thiếu cả 1 bảng). Luôn `git diff --stat -- DATABASE.md schema_annotations.yaml` khi diff có đổi `schema.prisma`. — `Áp dụng khi: db-schema`
- **Đảo/sửa giá trị 1 hằng số enum-like dùng CHUNG (vd `CONDITIONAL_MATCH`/`CONDITIONAL_DISPLAY` trong `option-set-validation.constant.ts`) rất rủi ro nếu không audit hết nơi dùng**: hằng số này từng lệch so với nguồn thật `cms/tae` (tên field bị đảo, giá trị số thì không đổi theo). Khi review 1 fix đổi *giá trị* của hằng số dùng chung, PHẢI tự grep toàn repo mọi nơi dùng tên hằng số đó (không chỉ trong diff) — kể cả nơi hardcode raw số `0`/`1` thay vì import hằng số (rủi ro cao nhất, vì không có compiler nào bắt được lệch nghĩa). — `Áp dụng khi: logic`
- **Sentinel string do V1 tự điền khi field rỗng** (`mapOptionSetToStorefront`: `label_on_product: option['labelOnProduct'] || 'Default Label'`) khiến downstream code đọc thẳng field đó (`label_on_product`) không bao giờ thấy chuỗi rỗng — check kiểu `if (!label)` sẽ luôn `false`, phải check đúng sentinel string thay vì check rỗng. Khi review mapper đọc dữ liệu đã qua `mapOptionSetToStorefront`, để ý các cột có logic `X || 'default...'` tương tự — check rỗng ở tầng sau nó sẽ luôn là dead code. — `Áp dụng khi: logic`

- **Fix "duyệt hết N phần tử" phía service nhưng query GraphQL nguồn vẫn giới hạn `first: 1`** (`PRICE_LISTS_QUERY` trong `common/gql/queries/markets.gql.ts` — file này thường KHÔNG nằm trong diff) → vòng lặp mới không có thêm dữ liệu; spec mock tên query (`'Q_PRICE_LISTS'`) và tự dựng nodes nên test vẫn xanh. Khi diff sửa code duyệt connection/list từ Shopify, mở luôn file `*.gql.ts` tương ứng để xem `first:` thật. — `Áp dụng khi: logic, external-call`

## Trọng tâm cần soi kỹ nhất
- Diff đổi `prisma/schema.prisma` → luôn kiểm tra `DATABASE.md`/`schema_annotations.yaml` có cập nhật kèm không.
- Diff thêm/sửa cron hoặc batch job đọc theo lô (`take`/`limit`) → kiểm tra có cơ chế xoay vòng khi vượt kích thước lô không.
- Diff trong `storefront-v2-sync/` (hoặc module dual-write tương lai) → đối chiếu với plan/spec .md tương ứng, không chỉ soi code tự thân; đặc biệt soi có bảng "sync state"/idempotency nào bị thiếu so với plan không.
- Mọi lệnh Shopify Admin API mới → có bọc retry nhất quán, có đọc `userErrors` trước khi coi là thành công/thất bại không.

## Không áp dụng / bỏ qua (giảm nhiễu)
- Không có surface `ui`/`webhook` trong repo này (backend API thuần, không render UI, chưa có webhook handler trong các module đã review) — bỏ qua Core Web Vitals, Embedded frontend, Webhook/Compliance section của `shopify-app.md` trừ khi diff thực sự thêm các surface đó.
